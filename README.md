# wrapfile

当前版本提供命令行版本查询与备份密钥生成。

## 构建与运行

```sh
cargo build --offline
./target/debug/wrapfile --version
```

输出：

```text
wrapfile 0.1.0
```

## 生成密钥文件

后续加密备份所需的密钥通过 `keygen` 子命令生成：

```sh
./target/debug/wrapfile keygen path/to/backup.key
```

成功时以状态码 0 结束，并在标准输出简短提示保存位置，例如：

```text
Key saved to path/to/backup.key
```

### 路径在提示中的显示

成功提示、创建或保存失败、清理未完成的警告，以及未知选项错误，都会用
**同一种方式**显示你给出的路径，且显示文字只供阅读——实际的创建、查找和
删除始终使用你传入的**原始路径**，不会在加了引号或反斜杠的名字下操作文件。

- **普通路径原样显示**：路径是合法 UTF-8，且不含 ASCII 控制字节、双引号
  `"` 和反斜杠 `\` 时，显示与以前完全一致，例如
  `Key saved to path/to/backup.key`；中文等可以正常显示的字符也保留原貌。
- **其余路径用双引号包住，并对特殊字节做转义**：
  - 换行、回车、制表符分别显示为两个字符 `\n`、`\r`、`\t`——文件名里的
    换行不会把一条提示拆成多行；
  - 双引号显示为 `\"`，反斜杠显示为 `\\`；
  - 其余 ASCII 控制字节（包括 ESC 等）和**无法组成合法 UTF-8 的原始字节**
    显示为 `\xhh`，`hh` 是该字节的两位小写十六进制值。

  因此提示中不会残留任何原始控制字节（每条消息自身结尾的换行除外），ESC
  等字节也不会原样进入终端产生控制效果；两个只是非 UTF-8 字节不同的名字
  （如一个含 `0xff`、另一个含 `0xfe`）也不会再显示成同一串替代字符。

- **转义表示没有歧义**，请按下面的方式阅读，不要把反斜杠序列误当成名字里
  真的多了字符：
  - 名字里确有一个 `0xff` 字节时显示为 `"key-\xff"`；名字里若真的依次写着
    反斜杠、`x`、`f`、`f` 四个字符，则显示为 `"key-\\xff"`。两者可见表示
    不同，对应两个不同的文件。
  - 同理，真实换行显示为 `"a\nb"`，而反斜杠后接字母 `n` 的名字显示为
    `"a\\nb"`。
- 引号以及 `\n`、`\xff` 等序列**只是提示里的写法，不是文件名的一部分**。
  若要照提示手动操作该文件，请按转义规则还原出真实名字（例如 `\xff` 是一
  个字节、`\n` 是一个换行），而不是把引号和反斜杠也照抄进文件名。

### 密钥文件格式

- 内容是**恰好 32 字节的原始二进制密钥**。
- 不含任何文本编码（如 hex/base64）、换行、文件头或其他附加字节。
- 密钥字节来自操作系统的密码学安全随机源（由成熟的 Rust 库
  [`getrandom`](https://crates.io/crates/getrandom) 提供，Linux 上为
  `getrandom(2)` / `/dev/urandom`），与时间、路径等无关，不可推算。
- 命令的标准输出与错误信息都不会包含或展示密钥字节。

### 文件权限

在 Unix 系统上，成功生成后留在磁盘上的密钥文件权限**恰为 `0600`（仅当前用户
可读写）**，无论 umask 宽松还是严格都一样：

- **不依赖默认 umask**：umask 宽松（如 `0000`）时，组和其他用户也不会获得任何
  权限；umask 严格（如 `0777`，会连同所有者权限一起屏蔽）时，命令会在写入前
  重新设置并确认权限，`0400`、`0200`、`0000` 都不会被当作成功结果。
- **从创建那一刻起就不暴露**：文件以不含组/其他权限位的模式创建，不会先以宽松
  权限开放、再在结束时收紧。
- **先确认权限，再写入密钥**：在写入任何密钥字节之前，命令会显式将权限设置为
  `0600`（该设置不受 umask 影响），并再次读取文件状态、确认权限位恰好是
  `0600`（所有者可读可写，组和其他用户无任何权限）。
- **无法保证权限则失败**：如果底层文件系统拒绝设置、或无法确认这一权限，命令以
  **状态码 1** 失败，在标准错误说明权限问题，并**删除本次生成的文件**；若系统
  拒绝删除，标准错误会同时说明清理未完成、目标处可能仍有本次生成的文件（见下
  文"失败后的清理"）。不输出成功提示；已有的其他文件和目录权限不会被改动。

### 拒绝覆盖与路径要求

生成操作只接受一个尚不存在的路径，以下情况都会**失败（状态码 1）**，且已有的
文件、目录或符号链接及其内容保持原样：

- 目标位置已存在任何文件、目录或符号链接（包括指向不存在位置的悬空符号链接；
  命令不会沿符号链接创建文件）；
- 目标的父目录不存在——命令**不会自动创建父目录**；
- 父目录不可写、随机源不可用、写入未完成，或无法将权限设置并确认为 `0600`
  （包括严格 umask 导致所有者权限缺失、文件系统不支持所需权限的情况）。

失败后命令会删除本次操作创建的文件，也不会改动原先存在的对象。

### 失败后的清理

无论失败发生在哪一步（权限设置或确认、写入、同步、关闭），命令都会尝试删除
**本次运行创建**的目标文件——不留空文件、不留部分密钥、也不留未保存成功的完整
密钥，原先存在的对象始终不受影响。

- **删除成功**时，目标路径不留下本次操作的任何产物。
- **删除被系统拒绝**（例如权限不允许）时，命令仍以状态码 1 结束、标准输出为空，
  但标准错误会同时给出：最初的失败原因（可分辨是权限无法保证、写入未完成还是
  同步失败）、清理失败及其原因，并明确提示**目标位置可能仍有本次生成的文件**
  ——哪怕留下的只是空文件——需要用户自行检查并删除。提示一定包含目标路径，不会
  用删除错误顶替保存错误，也不会声称文件已被移除。命令不会为了完成清理去修改
  父目录权限，也不会把文件改名另存；同目录已有文件的内容与权限保持原样。看到
  该提示后，请检查目标路径并手动删除残留，**不要把它当作可用密钥**。

### 关闭阶段的失败

保存只在全部 32 字节写入、同步（fsync）并且**正常关闭**之后才算完成。如果
关闭密钥文件时报告了不可恢复的错误（Linux 上仅返回 EINTR 的中断不算失败，
描述符已被释放，仍正常报告保存位置），即使目标文件恰好已有 32 字节、权限
恰为 `0600`，也**不算成功**：命令以状态码 1 结束，标准输出为空，标准错误
说明密钥保存未能正常完成、指出目标保存位置并说明问题发生在关闭密钥文件时，
同时像其他失败一样**删除本次生成的文件**。

如果关闭已失败、系统又拒绝删除本次目标（例如删除被权限拒绝），命令仍返回
状态码 1；此时标准错误既保留原先的关闭失败原因，也明确告知清理未完成、
目标处可能仍留有本次的密钥文件——不会只报告保存错误，也不会声称没有残留。
命令不会为了完成清理去修改父目录权限，也不会把密钥改用另一个名字留下；
目录中的已有文件及其内容和权限保持原样。看到该提示后，请自行检查并删除
目标处的残留文件。

### 参数与状态码

- `wrapfile --version`：输出版本号，状态码 0。
- `wrapfile keygen <密钥文件路径>`：成功状态码 0，生成失败状态码 1。
- 缺少路径、多给参数、使用未知选项（或任何无法识别的调用）：状态码 2，
  并在标准错误显示用法，不生成任何文件。

```text
Usage: wrapfile --version
       wrapfile keygen <KEY_FILE>
```

### 密钥的保管

密钥文件是**秘密**，应当像密码一样妥善保管（避免放入公开目录、代码仓库、
日志或随备份明文外传）。密钥只存在于这 32 字节中，**一旦遗失，无法凭文件名、
生成时间或任何其他信息恢复其中的密钥**，用它加密的备份也将无法解密。请自行
安排安全、可靠的密钥备份（例如离线副本），并确保副本同样不被他人读取。

## 权限约定的回归测试

`cargo test` 会对上述文件权限约定做自动化回归保障（Unix，当前工具链为
Linux/glibc；在其他系统上相关用例会自动跳过）：

- 在进程内 umask `0022` / `0000` / `0777` 下分别运行 keygen，断言恰好
  32 字节、最终权限恰为 `0600`、标准输出只有保存位置提示、且 stdout/stderr
  都不含密钥字节。
- 通过 `tests/support/permfail` 提供的 LD_PRELOAD shim，从进程内部记录
  `open`/`fchmod`/`fstat`/`write` 时序，断言文件从创建那一刻起组/其他位即
  全部关闭，并在**任何密钥字节写入之前**已经把权限设为并经 `fstat` 确认为
  `0600`（首次 `write` 前 size 为 0、mode 为 `0600`）。
- 用同一 shim 注入故障：`fchmod` 返回 EPERM、`fstat` 无法完成、以及文件
  系统谎报存储的 mode（`0000`/`0644`）。断言命令返回 1、stderr 说明权限
  问题、无成功提示、未写入任何密钥字节、本次目标被清理，且父目录及兄弟
  文件/inode/内容/权限均不被改动。若删除同时被拒绝（unlink 注入 EACCES），
  断言 stderr 既保留权限问题、也报告清理失败并提示目标处可能仍有本次生成
  的文件（即使只是空文件），残留不被改名另存，父目录权限不被改动。
- 覆盖已有文件、目录、悬空符号链接（不跟随、不替换）、父目录缺失等既有
  保护规则，以及 `--version` 与参数错误退出码 2 的行为不变。

`tests/keygen_write_safety.rs` 保障写入与同步契约（同样借助 permfail shim
注入故障并记录每次 `write`/`fsync`）：

- 每次 `write` 只接受部分字节时，剩余字节继续写入，不重复、不遗漏，最终
  文件恰好是 32 字节原始密钥；`write` 被 EINTR 打断后重试仍能完成同一次
  生成（状态码 0）。成功只在全部字节写入并 fsync 之后报告。
- 写入中途出现不可恢复错误、或全部字节写入后 fsync 失败：状态码 1，
  stderr 说明失败并指出目标路径，stdout 无成功提示，本次创建的文件被删除，
  父目录权限与已有兄弟文件不受影响。
- **写入没有前进**：还有字节待保存时 `write` 返回接受了 0 字节且没有报告
  任何错误——这既不同于每次仍有进展的短写，也不同于可恢复的中断。无论
  发生在尚未写入任何字节时、还是已写入 10 字节后，命令都必须结束（不会
  卡在保存循环里）并以状态码 1 失败：stdout 为空，stderr 说明密钥文件
  未能写完并指出目标路径；目标位置不留空文件、不留 10 字节残片、也不
  补零凑成 32 字节；父目录权限与已有文件保持原样；已取得或已保存的密钥
  字节不以原始或 hex 等形式出现在 stdout/stderr。故障消除后同一路径可
  正常重试成功。
- **关闭阶段失败**：全部 32 字节写入并 fsync 后，close 报告不可恢复错误
  （shim 在真正释放描述符后注入 EIO）也算保存失败——即使目标已有 32 字节、
  权限恰为 `0600`，仍返回 1、stdout 为空、stderr 说明问题发生在关闭密钥
  文件时并指出目标路径，本次文件被删除，父目录权限与兄弟文件不受影响。
  若系统同时拒绝删除（unlink 被注入 EACCES），仍返回 1，stderr 既保留关闭
  失败原因、也明确告知清理未完成且目标处可能仍有本次密钥文件；不为清理
  修改父目录权限，也不改用其他名字留下密钥。而 close 仅返回 EINTR（描述符
  已释放）不算失败：仍正常报告保存位置并返回 0。
- **写入/同步阶段失败且删除被拒绝**：写入中途不可恢复错误、fsync 失败、或
  写入零进展，同时 unlink 被注入 EACCES 时，仍返回 1、stdout 为空；stderr
  保留最初的失败原因（可分辨写入未完成还是同步失败）、报告清理失败及其原因，
  并明确提示目标位置可能仍有本次生成的文件（部分密钥、未同步的 32 字节、或
  空文件都如实交代），提醒用户自行检查删除；残留不被当作成功、不补齐、不改名，
  父目录权限与兄弟文件保持原样。

另有 `tests/keygen_unix_paths.rs` 保障 Unix 下的路径处理规则：生成操作只使用
用户交给命令的原始路径，显示提示时的文字渲染不决定实际创建或拒绝创建哪个
文件：

- 含非 UTF-8 字节的合法文件名可正常生成（状态码 0、恰好 32 字节、权限
  `0600`、stdout 保留保存位置提示、stderr 为空），且不会因显示转换额外创建
  文件名含 U+FFFD 替代字符的文件。
- 同一目录下两个原始字节不同的名字互不混淆、渲染也互不相同（一个显示
  `\xff`、另一个显示 `\xfe`）：目标是否存在只按原始路径判断；显示不同的
  兄弟文件不被当作目标、不被改写或改权限；原始目标已存在时返回 1、保留
  已有内容与权限，也不会转而在显示后的名字下生成。
- 紧跟 keygen 的 `--` 之后的唯一参数按文件名处理（即使以 `-` 开头或同时含
  非 UTF-8 字节）；没有 `--` 时以 `-` 开头的参数仍是未知选项错误（状态码 2、
  stderr 显示用法、不留新文件）；`--` 不改变只接收一个路径的要求。
- 路径显示规则本身也有回归保障：含换行/回车/制表符/ESC 等控制字节、双引号、
  反斜杠或非 UTF-8 字节的名字，在成功提示、创建错误和清理未完成警告中都
  按同一规则加引号并转义；成功行与错误行除自身结尾换向外不含任何原始控制
  字节，名字不会把提示拆成多行。真实 `0xff` 字节（显示 `\xff`）与名字里
  真写着 `\xff` 四个字符（显示 `\\xff`）、真实换行（`\n`）与反斜杠加字母
  `n`（`\\n`）的可见表示两两不同；断言文件实际只在原始名字下生成，转义
  后的名字下没有任何文件。未知选项（包括带换行或非 UTF-8 字节的选项）也
  遵守同一显示规则。

`tests/keygen_random_source.rs` 保障随机源不可用时的行为。getrandom crate
以内联汇编直接发起系统调用，符号拦截（如 permfail 所用的方式）看不到它，
因此 `tests/support/randtrap` 这个 shim 改用 seccomp（`SECCOMP_RET_TRAP`）
在进程内截获 `getrandom(2)`、由 SIGSYS 处理函数按环境变量配置模拟返回；
注入只作用于配置了故障的这一次运行，其他进程与其他调用仍使用真实随机源
（x86_64/aarch64 之外的架构不构建该 shim，相关用例自动跳过）：

- 随机源在交出任何字节前就失败：状态码 1，stderr 说明密码学安全随机源
  不可用（不绑定随系统变化的底层错误文字），stdout 为空；目标位置不出现
  空文件、部分密钥或看似完整的替代密钥，目录里也不留下本次操作产生的
  其他文件。
- 已交出部分字节、在补足 32 字节前不可恢复地失败：同样状态码 1 且不保存
  任何文件——已取得的字节不被补零成"完整"密钥保存，也不以原始字节或 hex
  等文本编码形式出现在 stdout/stderr 中。
- 每次只返回部分字节、但始终可继续读取的随机源不算失败：命令持续读取直到
  取齐 32 字节并正常成功（文件内容逐字节等于随机源交付的内容，权限恰为
  `0600`，stdout 保留保存位置提示）。
- 失败发生在有其他文件的目录里时，已有文件的内容与权限、父目录权限、以及
  目标位置本来存在的文件或符号链接（连同链接指向的对象）都保持原样。
- shim 加载但不配置故障时使用真实随机源，正常生成仍是恰好 32 字节、权限
  `0600`；故障配置下 `--version` 与参数错误（状态码 2）行为不变，瞬时失败
  后的重试可正常成功。

两个 shim 由 `build.rs` 调用系统 `cc` 编译进 `OUT_DIR`，不引入任何新的 Rust
依赖（仍可 `cargo test --offline`）。
